## THE LAST OPEN QUESTION, ANSWERED — 2026-09-05

  Does a per-player block reach the CHALLENGE?  YES, when it is unambiguous.

  C5 split submitting and voting into two independently controlled capabilities, which left
  the challenge belonging to neither: an administrator who blocked somebody from submitting
  AND voting after an investigation had not stopped them playing the winning map and winning
  the month's prize. That was a hole, not a policy.

  THE RULE, canEnterChallenge in server/src/repo/users.ts, gated by requireCanChallenge:

    blocked from BOTH submit and vote   refused
    granted BOTH                        allowed, whatever the country says
    anything else, including partial    the country allowlist decides (E2, unchanged)

  Why derived rather than a third column: the two capabilities an administrator actually sets
  are the only inputs, so there is nothing extra to keep in sync, no migration, and no policy
  frozen into the schema before it has been used in anger. Why not
  canParticipate('submit') && canParticipate('vote'): that reads every PARTIAL block as a
  challenge ban, and "no submitting for a month" after a troll entry says nothing about
  playing the winning map.

  Carried through to the client as ApiUser.canChallenge, so the dashboard states the verdict
  instead of offering a button that can only answer 403 — the same fix C5 made to the submit
  page. The admin Users tab shows it as a read-only column beside the two switches that
  produce it, because "did blocking both actually stop them competing?" is exactly the
  question those switches raise.

  NOTHING IN THIS ROADMAP IS WAITING ON A DECISION.

## WHAT CHANGED SHAPE, for anyone reading the code cold

  Five things moved that are worth knowing before editing:

  1  requireEligible NO LONGER EXISTS. C5 split it into requireCanSubmit and
     requireCanVote, resolved through canParticipate in repo/users.ts. The challenge has its
     own gate, requireCanChallenge, resolving canEnterChallenge — the country rule unless an
     override blocks or grants BOTH capabilities. THREE gates now, one rule file.
  2  isEligible and canParticipate are PURE and take their inputs. The allowlist and the
     per-player override are loaded by the caller, through the caches in
     repo/allowedCountries.ts and repo/participantPermissions.ts. That is what keeps the
     gate and the canSubmit / canVote flags on ApiUser one sentence rather than two.
  3  THE SESSION COOKIE HAS THREE FIELDS NOW: osu id, expiry, revocation epoch. A cookie
     with only two reads as epoch 0, which is the column default, so old cookies work.
  4  ALLOWED_MODS and ALLOWED_CHALLENGE_TYPES are SEEDED_MODS and SEEDED_CHALLENGE_TYPES.
     They seed site_settings and are no longer the rule — but they still document which
     challenge-type NAMES carry behaviour, because repo/challengeScores.ts switches on
     those strings in qualifies() and orderFor().
  5  sampleData.ts IS GONE. Nothing in src/ renders invented data. If a page needs an
     example, it needs an endpoint.

# THE WINNER STATE MACHINE  (D1 + B10 + C2, in one place)

  rounds gains winner_status, one of:

    none        the round has not finished voting
    pending     voting closed, one clear top entry, awaiting admin approval
    tiebreak    voting closed, two or more level at the top, awaiting an admin
                choosing between them
    official    an admin approved it; permanent

  voting_ends_at passes (C2), or an admin ends voting by hand
        │
        ├── exactly one highest count ──> winner_status = 'pending'
        │                                 winning_submission_id = that entry
        │                                 winner_vote_count, total_votes frozen
        │                                 phase stays 'voting'
        │                                 admin approves ──> 'official', phase 'challenge'
        │
        └── two or more tied ──────────> winner_status = 'tiebreak'
                                          tied entries recorded, no winner set
                                          phase stays 'voting'
                                          admin selects one ──> 'official', phase 'challenge'

  A VALIDLY CAST VOTE IS PERMANENT. Blocking a voter later (C5) only stops them
  voting again; it never removes a vote already cast. Rejecting a submission after
  votes were cast for it does not retroactively delete or discount those votes
  either. The only way a recorded result changes is an administrator performing an
  explicit, separate result correction (D4) — never as a side effect of a block or
  a review. So "highest valid vote count" means: every vote that was validly cast
  while the ballot was open, counted as cast.

  THE BALLOT CLOSES ON winner_status, NOT ON THE PHASE. The vote endpoints
  currently gate on phase === 'voting' alone; they must also require
  winner_status === 'none', or votes would keep landing while a winner sat pending
  and the frozen counts would stop matching the table.

  The owner asked for an Algeria-only performance ranking page, modelled on
  https://osu.ppy.sh/rankings/osu/global but with its own point system: points earned
  EXCLUSIVELY by playing the monthly challenges, never imported from osu! pp or ranked-score
  data. Challenge performance, accuracy, completion/results and difficulty/placement all
  contribute, and the leaderboard is cumulative across challenges.

  THIS LIFTS A BAN, AND THE BAN'S WORDING IS WHY IT CAN BE LIFTED. my_plan.txt:940-947
  forbids inventing "points systems" and "ranking systems not specified by the owner". A
  ranking the owner specifies is not the thing that was forbidden — and :950 says what to do
  with the parts still unspecified: "leave room for extension and ask the owner rather than
  creating a complicated feature." So every number below is a PROPOSAL carrying its reasoning,
  and the five questions closing this section are the ask. No code until they are answered.

  ── WHAT THE DATA ALREADY SUPPORTS ──────────────────────────────────────────

  The formula was designed backwards from columns that already exist, so it needs no new osu!
  API call, no new import path and no change to how a score is recorded. Per player per round:

    challenge_scores   score, accuracy, misses, mods, qualified, submitted_at.
                       ONE ROW PER USER PER ROUND (challenge_scores_one_per_user_per_round),
                       and it already holds their best play. `qualified` is computed on insert
                       and STORED "so past rounds keep their verdict if the rule changes"
                       (002_challenge_scores.sql) — the precedent this whole section follows.
    rounds             round_number, month, year, winner_status, winning_submission_id
    submissions        the winning map's stars, mod_requirement, challenge_requirement
    users              country_code — the Algeria filter

  Nothing here reads users.global_rank, which stays display-only: DELIBERATELY ABSENT still
  bans vote weighting by osu! rank, and importing pp is exactly what the owner ruled out.

  ── THE PROPOSED FORMULA ───────────────────────────────────────────────────

    RoundPoints = round( difficultyFactor × ( base + placement + accuracy + bonuses ) )

  1  BASE — completion.            submitted any score at all      10
                                    the score qualified            +25
     `qualified` means it met the round's mod requirement and, on a Full Combo round, had no
     misses. A non-qualifying play still earns the 10: turning up and failing the terms is
     worth more than not turning up, and less than doing it properly.

  2  PLACEMENT — 100 × (1/√r) × fieldFactor, qualified plays only.
     Rank r comes from the round's OWN ordering, orderFor() in repo/challengeScores.ts —
     score DESC normally, accuracy DESC on a Best Accuracy round, misses ASC on a Lowest Miss
     Count round. Ranking by raw score everywhere would contradict the leaderboard the players
     were shown.
       1/√r decays gently:  1st 1.00   2nd 0.71   3rd 0.58   4th 0.50   5th 0.45   10th 0.32
       1/r was rejected — halving the winner's points for second place is brutal in a field
       of four, which is the field this community actually has.
       fieldFactor = min(1, N/8), N = qualified players that round. THE SMALL-FIELD FIX, and
       the single most important number in this proposal: winning a 3-player round scores
       100 × 1.00 × 0.375 = 38, not 100. Without it the earliest months — when turnout is
       lowest — mint the most points, the first few players lock the table permanently, and
       the ranking stops measuring anything as the community grows.

  3  ACCURACY — 60 × ((max(0, acc − 80) / 20)²), capped at 60.
       80% or less 0    90% 15    95% 34    98% 49    99% 54    100% 60
     Squared, not linear, because 90% and 99% are numerically 9 apart and nothing alike to a
     player. Floored at 80% so a wildly failed play earns nothing here, capped at 60 so
     accuracy cannot outrank placement.

  4  BONUSES — kept small on purpose.
       your submission won the round                                   +20
       full combo on a round that did NOT require one                   +10
     No points for voting, deliberately. B11 made ballot secrecy a rule; paying for votes
     turns the ballot into currency and invites farming the one thing that has to stay clean.

  5  DIFFICULTY — difficultyFactor = clamp(0.8, 1.4, 0.8 + (stars − 4) × 0.1)
       3★ and under 0.8   4★ 1.0   5★ 1.1   6★ 1.2   8★ and over 1.4
     The winning map's stars are identical for everyone in a round, so difficulty cannot
     separate players WITHIN a round — it separates ROUNDS from each other, which is why it is
     a multiplier on the whole round rather than a term in the sum. Clamped so one absurd map
     cannot distort the table.

  WORKED EXAMPLE — 5★ map, Full Combo required, 6 qualified players, you place 2nd at 97.5%
  with no misses:
       base       10 + 25                                   =  35
       placement  100 × 0.707 × (6/8)                       =  53
       accuracy   60 × ((17.5/20)²)                         =  46
       bonuses    FC was required, so already priced in      =   0
       subtotal                                                134
       × 1.1 for 5★                                        =  147 points

  ── THE CUMULATIVE LEADERBOARD ──────────────────────────────────────────

  TotalPoints = Σ RoundPoints. A plain sum — no decay, no "best N of M".

  osu! weights pp by 0.95^i because a player has thousands of plays and ancient farm scores
  would otherwise dominate. Here there are twelve rounds a year, each unrepeatable, and the
  thing being rewarded IS sustained monthly participation. Decay would punish exactly the
  loyalty this page exists to show.

  The cost of a plain sum: whoever joined first is permanently ahead of a newcomer who plays
  better. The fix is not decay but a SEASON — rounds.year already exists, so a calendar-year
  table plus an all-time table costs one WHERE clause. That is question 2 below.

  ── THE ORIGINAL WORDING OF THOSE QUESTIONS ────────────────────────────────

  Q1  WHO APPEARS?  The owner said Algerian users only, no other countries. But C4 replaced
      the hardcoded ELIGIBLE_COUNTRY = 'DZ' with the allowed_countries table precisely so the
      rule would be configurable, and that table holds DZ alone today. Two readings:
        (a) filter on the allowlist — one rule for competing and for ranking, so if MA is ever
            enabled, Moroccans who played appear. Recommended: a player who was allowed to
            compete and did compete has earned points, and a table that hides them is lying.
        (b) hardcode 'DZ' — literally what was asked, and it means the allowlist and the
            ranking can disagree the moment a second country is enabled.
      RECOMMEND (a). It is DZ-only today either way, so this only decides the future.

  Q2  SEASONS?  A plain cumulative sum makes the earliest joiner permanently top. rounds.year
      exists, so a per-year table costs a WHERE clause.
      RECOMMEND both, all-time as the default view and a year selector beside it.

  Q3  FROZEN OR DERIVED?  (a) migration 013 storing one row per user per round, written when
      the challenge phase ends — history stable, the owner applies the DDL. (b) computed at
      read time from challenge_scores every request — no migration, always consistent with the
      data, but tuning a constant silently rewrites every past month and the query grows
      forever.
      RECOMMEND (a), on the precedent of challenge_scores.qualified and D4.

  Q4  WHERE DO THE CONSTANTS LIVE?  (a) code constants, changed in a commit and reviewable in
      a diff. (b) site_settings rows, editable in the admin config tab.
      RECOMMEND (a) for v1. Admin-editable point weights mean the leaderboard can be reshaped
      from a settings form with no record of who reshaped it — a governance hole, not a
      feature. C8 put beatmap RULES in site_settings because they gate submissions before the
      fact; points describe results after it, and those are not the same kind of setting.

  Q5  DO NON-QUALIFYING PLAYS SCORE?  RECOMMEND yes — the 10-point base, no placement, and
      accuracy points as normal. Zero for a failed attempt reads as punishment for entering,
      and `qualified` is already stored per round so the distinction is free.
